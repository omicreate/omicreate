# またね帳 MVP仕様（プロトタイプ用）

- 作成日: 2026-11-07 ／ 版: 0.1
- 作るもの: このセッション内で動くプロトタイプ（React + Vite + PWA、TypeScript、Vitest、Playwright）
- 前提: 無料・登録不要・広告なし・Cookieなし・オフラインで動く・記録は端末内だけ（IndexedDB）。サーバー、外部API、APIキー、決済、ログインは使わない。外とのやりとりは、利用者が自分で押す「コピー」と「LINE共有リンク」、ファイルの書き出しと読み込みだけ。
- 根拠の表記: **事実**＝調査で出典を確認できたもの／**推定**＝調査の換算・試算・少数の声からの推し量り／**未検証**＝確かめていないもの。画面の初期値やしきい値のうち出典のないものは、すべて**仮の値**と書き、設定で変えられるようにする。

## 1. 一言で・名前

- **名前: またね帳（またねちょう）**
  - 「またね」はお客様を見送るときの言葉で、会計時に次回の約束を残す道具であることを表す。既存の美容系サービス名（SALON BOARD、minimo、LiME、美歴、LINEビューティープラスなど）と音も字面も重ならない一般語の組み合わせにした。
  - **未検証**: J-PlatPat での商標検索はこのセッションではしていない（Web検索なし）。公開前に確認し、紛らわしい登録があれば名前を変える。
- **一言で**: 個人美容師が会計の30秒で「次回の目安」を残しておくと、記録の抜けを確かめたうえで「声をかけてもよさそうな人」を数人だけ示してくれる再来ノート。送るのは自分の言葉で、自分のLINEかコピーで。記録はこの端末の中だけ。
- **誰の**: シェアサロン・面貸し・業務委託で独立して1〜3年目の個人美容師。
- **何を**: 常連が静かに離れていくのに気づくのが遅く、声をかけるきっかけも言葉もないこと。
- **どう解く**:
  0. 前提として、記録が抜けていないかを毎回確かめる（今日のお客様・来た？の確認・最終来店の確認）。
  1. **予防**: 会計時に次回の約束（目安か予約日）を残し、「またねカード」で本人にも渡す。
  2. **発見**: その人の約束と実際の周期から「次回の目安日」を出し、過ぎた人を数人だけ示す。
  3. **回復**: 前回の内容を差し込んだ下書きを自分の言葉に直し、自分で送る。

## 2. 対象者と利用場面

### 2.1 主な対象（想定）

- シェアサロン利用者、面貸し、業務委託で独立して1〜3年目。30歳前後、スマホ1台で仕事を回し、ネットに慣れている（market の示唆どおり若い独立層を主対象にする）。
- 予約は HPB・minimo・個人LINE・電話などを併用している。統合型の顧客管理ツール（LINEビューティープラスなど）のリマインドは使っていない。
- 前回の施術は紙カルテ、メモアプリ、予約サイトの履歴に散らばっている。
- 会計時に「次は6週くらいですね」と話すことがある、または話してもよいと思っている。
- 副対象: 若い1人サロンのオーナー。業務委託でサロンの屋号・サロンの集客で働く人も使えるが、サロン由来の顧客には制限をかける（7.3）。

### 2.2 対象にしない・合わない人

- 60歳以上のオーナー層（経営者の56%）。使えないようにはしないが、プロトタイプでは画面や文言をこの層に合わせない。
- 統合型ツールで予約・リマインド・分析をすでに回している人。そちらのほうが入力が少ない。
- 予約サイトのリマインド配信やクーポン配信で再来を回したい人。またね帳は自動配信をしない。
- 1台の端末を複数のスタッフで共有する店。1人1台の前提で作る。

### 2.3 利用場面（いつ・どこで・何秒で）

所要時間はすべて**設計上の目標**で、調査で得た数字ではない。試用で測る。

## 3. 解く困りごとと根拠

### 3.1 解く困りごと

**「お客様が静かに離れていくのに、気づくのが遅く、声をかけるきっかけも言葉もない」**。あわせて、その前提になる「前回の内容をすぐ思い出せない」を、顧客カードの前回表示で軽く解く。

- **課金余地**（月1,000〜3,000円）: 根拠データがない。この仕様は無料で、収益を前提にしない。
- **DM返信の負担**: 根拠は開発者 note の例示だけ。DM一本化は扱わない。
- **キャンセル率の重さ**: 17.24%は事前取消を含む率で、無断キャンセルは1.80%。キャンセル対策は扱わない。
- **紙カルテが主流**: 根拠は n=23 の調査と約10店舗。紙からの置き換えを売りにしない。
- **「再来が年0.1回増えれば約24万円」**: 前提の多い試算（推定）なので、画面にも訴求にも使わない。
- **予約経路の分散が大きな負担**: 個人美容師の経路構成は誰も調べていない。予約の一本化は扱わない。

## 4. MVPの機能（画面ごと）

### 4.0 共通

- 下のタブ: ［ホーム］［お客様］［ボード］［設定］。ホームには［来店を記録］の大きなボタンを常に出す。
- ボタンは指で押しやすい大きさ（目安44〜48px以上）。片手で操作できる配置にする。
- 日付は端末のローカル日付で扱う。アプリを開いたまま日付が変わったら、画面に戻ったとき（visibilitychange）に再計算する。
- 入力中のフォームは自動で下書き保存する（6.1）。削除は直後10秒間「元に戻す」ができる。
- 文言は「声をかけてもよさそうな人」「ご無沙汰」など、責める言い方を避ける。「失客」という語は画面に出さない。
- サンプル表示中は、すべての画面の上部に「サンプル表示中」の帯を出す。

### 4.1 S0 はじめに（初回だけ）

- **目的**: データの持ち主と保存場所を最初に伝え、サンプルで試すか自分のお客様で始めるかを選んでもらう。
- **表示**:
  - 3つの約束: (1) 記録はこの端末の中だけに保存される。(2) 作り手（omicreate）は記録を受け取らず、見ることもできない。消えたら作り手は戻せない。(3) 所属サロンから引き継いだ顧客や、サロンの集客で来た顧客のデータは所属サロンのもの。このアプリを違法な持ち出しや勧誘に使わない。
  - 「またね帳はカルテの代わりではありません。アレルギーなど安全に関わる記録は、今お使いのカルテで管理してください。」
  - iPhone では「ホーム画面に追加」して使うとデータが消えにくい、という案内（7.5）。
  - ［読みました］チェック、［サンプルで試す］［自分のお客様で始める］。
- **操作**:
  - ［読みました］にチェックするとボタンが押せる。確認した日時と文面の版を Settings.notice に保存する。
  - ［自分のお客様で始める］→ 自分の名前（任意。文面の署名）→ 予約リンク（任意。自分用と所属サロン用）→ 使うメニューのチップを選ぶ（初期値は4.9）→ ざっくり登録（4.7）へ進む。
  - 途中で閉じても、次に開いたとき続きから始まる。
  - 本番で始めた時点で永続保存（navigator.storage.persist）を求める。
- **空の状態**: なし。
- **エラー時**: IndexedDB が使えない（プライベートブラウズなど）とき、「この状態では記録を保存できません。通常のブラウザで開くか、ホーム画面に追加してください」と出す。サンプルは保存なし（メモリ上）で試せるようにする。

### 4.2 S1 ホーム

- **目的**: 施術前に今日のお客様の前回を見る（毎日）。来た？の確認を片付ける。声をかけてもよさそうな人を数人だけ見る（週1回）。
- **表示**（上から順に）:
  1. **お知らせ帯**（必要なときだけ、優先順に1つ）: 「記録が止まっています（最後の来店記録から○日）」→［まとめて記録する］［休みでした］／「最後のバックアップから○日」→［バックアップする］／「ホーム画面に追加すると、データが消えにくくなります」（初回から7日間だけ）。サンプル表示中の帯は別に常に出す。
  2. **［来店を記録］**の大きなボタン。
  3. **今日のお客様**（6.7）: 呼び名、前回の日付とメニュー、レシピメモの1行目、会話メモの1行目、状態（［来た］ボタン／「記録済み」）。
  4. **来た？の確認**（6.7）: 呼び名、予約日、［来た］［別の日に来た］［来なかった］。
  5. **声をかけてもよさそうな人（○人）**（6.6）: 1本のリスト。各カードに次を出す。
     - 呼び名、区分バッジ（そろそろ／ご無沙汰／離れたかも）
     - 根拠がいつもの周期のとき「いつもは約8週ごと → 今回は11週」、会計時の約束のとき「会計時の目安 6週 → 今回は8週」、メニューか全体の目安のとき「目安 約90日（縮毛矯正）→ 99日」
     - 前回のメニュー
     - ラベル: 「連絡OKは未確認」「最終来店はおおよそ」「はじめて」
     - ［声をかける］
     - 上限は Settings.listLimit（仮の値5）。超えたら［ほかに○人］で開く。
  6. **出していない人の要約**: 「所属サロンの顧客 1人・連絡しない 1人・声をかけてから30日以内 1人は出していません」。タップで顧客一覧の該当フィルタへ。1年以上来ていない人がいれば「1年以上来ていない人 ○人」も出す。
  7. ［閉店後のまとめ記録］へのリンク。
- **操作**:
  - 今日のお客様の行をタップ → 顧客カード。［来た］→ 来店記録（客・今日の日付・前回と同じメニューが入った状態）。
  - 来た？の確認: ［来た］→ 来店記録（日付＝予約日、メニュー＝前回と同じ）。［別の日に来た］→ 来店記録（日付を選ぶ）。［来なかった］→ 予約を流れたことにする（Visit.bookingResolution = 'not_visited'）。10秒間取り消せる。
  - 声かけ候補のカード → S4 声かけ。
- **空の状態**:
  - 顧客が0人: 「まずはお客様をざっくり登録しましょう。呼び名と、最後に来た月だけで始められます」＋［ざっくり登録］［サンプルで試す］。
  - 今日のお客様が0人: 見出しだけ残し「今日の予約は入っていません。会計時に次回の予約日を入れると、ここに出ます」。
  - 声かけ候補が0人: 「今日は声をかける人はいません」。
- **エラー時**: データの読み込みに失敗したら「読み込めませんでした」＋［もう一度］と、バックアップからの復元の案内。計算できない顧客（来店記録なし）は候補に出さず、一覧で「最終来店を入れると目安が出ます」と出す。

### 4.3 S2 来店記録（会計）とまたねカード

- **目的**: 会計の30秒で、来店と次回の約束を残す。続けて、お客様に次回の目安を渡す。
- **表示**:
  - 1行入力の欄: 「1行で入れる（例: ゆず カットカラー 6週）」。キーボードの音声入力を使ってよい、という一言。
  - 客: 選択済みならその呼び名。未選択なら「最近のお客様」5人と、呼び名・かなの前方一致検索。
  - 日付: 初期値は今日。変更できる（未来の日付は不可）。
  - メニュー: チップ（複数選択）。先頭に［前回と同じ］。
  - 次回: ［4週］［6週］［2か月］［3か月］［おまかせ］［予約日を入れる］。未選択でも保存できる。
  - 連絡: ［OK］［しない］［未確認］（今の値を表示）。「目安のころにLINEでお知らせしてもいいですか？」という聞き方の例を小さく出す。
  - ▼くわしく（閉じた状態が初期値）: 金額（任意）、レシピメモ＋［前回のメモを複製］、会話メモ。メモ欄の下に常に「体質・病歴・妊娠など健康のことは書かないでください」。
  - ［保存］。
- **タップ数**（設計目標）: 今日のお客様の［来た］から開いた場合、［6週など次回のチップ］→［保存］で、［来た］を含めて**3タップ**。検索から開く場合は、文字入力のほかに客の選択・メニュー・次回・保存の4タップ。
- **操作**:
  - 1行入力の結果（6.11）はチップと欄に反映し、「読み取れなかった語」は欄の下に表示する。自動で保存はしない。
  - ［前回のメモを複製］は直近の来店のレシピメモをそのまま入れ、ColorRecipeMemo.copiedFromVisitId を記録する。
  - 保存すると、その客の状態を再計算する。リストから外していた客（archived）は自動で戻し、「リストに戻しました」と出す。
  - 保存後、**またねカード**のシートを出す: 差し込み済みの文面（4.10、編集可）、［LINEで送る］［コピー］［送らない］。［LINEで送る］か［コピー］のあとに「送りましたか？」［送った］［送っていない］を出し、［送った］なら ContactLog（kind 'matane'）を残す。
  - データの管理者が「所属サロン」の客では、またねカードに自分用の予約リンクを入れない（所属サロン用のリンクが設定されていればそれを入れ、なければ予約リンクの行を消す）。
- **空の状態**: 顧客が0人のとき、客の欄に「新しいお客様として登録」を出す。呼び名を入れ、データの管理者と獲得経路を選べば、その場で登録して記録を続けられる。
- **エラー時**:
  - メニュー未選択: 「メニューを1つ選んでください」（保存しない）。
  - 日付が未来: 「未来の日付は入れられません。次回の予約は『予約日を入れる』へ」。
  - 予約日が来店日以前: 「予約日は来店日より後の日付にしてください」。
  - 同じ客・同じ日の記録がすでにある: 「この日の記録がすでにあります」＋［その記録を開く］［それでも保存］。
  - 保存に失敗（容量不足など）: 下書きを残したまま「保存できませんでした。端末の空き容量を確認し、バックアップを書き出してください」。
  - クリップボードが使えない: 文面を全選択した状態で表示し、「長押しでコピーしてください」。
  - LINEが開けない（オフライン、LINE未インストールなど）: 「LINEを開けませんでした。コピーして送ってください」と出し、コピーを促す。

### 4.4 S3 閉店後のまとめ記録

- **目的**: 会計で記録しそびれた日に、今日の分をまとめて付け、記録を途切れさせない。
- **表示**:
  - 日付（初期値は今日。「昨日の分」に切り替えられる）。
  - その日の予約が入っていた人と、その日にすでに記録した人の一覧。各行に［来た］［来なかった］［未定］、メニュー（［前回と同じ］が入った状態、タップで変更）、次回のチップ。
  - ［＋人を足す］（検索）。
  - ［まとめて保存］。
- **操作**: ［来た］の行だけ来店記録を作る（source 'batch'）。［来なかった］の行は予約を流れたことにする。［未定］は何もしない。保存後に「○人を記録しました」と出し、10秒間まとめて取り消せる。
- **空の状態**: 「この日の予約は入っていません」＋［＋人を足す］。
- **エラー時**: 1行でも保存に失敗したら、成功した行と失敗した行を分けて示し、失敗した行は画面に残す。

### 4.5 S4 声かけ（送る前の確認）

- **目的**: 記録の抜けを確かめてから、自分の言葉に直した文面を、自分で送る。
- **表示**（上から）:
  1. 呼び名、区分バッジ、「いつもは約8週ごと → 今回は11週」と目安の根拠（例「いつもの周期（直近3回）」「会計時に決めた6週」「メニューの目安（縮毛矯正 2〜4か月、craft の記事）」「全体の目安 約87日（美容センサス2026上期から換算）」）。
  2. **記録上の最終来店**: 日付（曜日つき）、何日前か、メニュー。年月だけの登録なら「最終来店はおおよそ（2026年7月）」。最後の来店記録から8日以上たっているときは「記録が止まっています。最近の来店が抜けていないか確かめてください」を赤で出す。
  3. ［実は来ていた → 来店を追加］。
  4. 前回の会話メモ・レシピメモ（美容師が見るためだけのもの。文面には自動で入れない）。
  5. 文面（テンプレートを差し込んだ下書き。編集できる）。
  6. 宛先の目印: LINE表示名が登録されていれば「LINEで『○○』を選んでください」。なければ「送り先を選ぶとき、呼び名と取り違えないように注意してください」。
  7. ［LINEで送る］［コピー］（同じ大きさで並べる。LINE公式アカウントや Instagram DM でやりとりしている人はコピーを使う）。
  8. ［今回は見送る］（2週間／次の周期まで／連絡しないにする）。
- **操作**:
  - ［実は来ていた］→ 来店記録（客を選んだ状態、日付を選ぶ）。保存後にこの画面へ戻り、候補でなくなったら「リストから外れました」と出してホームへ戻る。LocalCounters.actuallyVisitedFixes を1増やす。
  - ［LINEで送る］→ `https://line.me/R/share?text=` に文面を URL エンコードして付けたリンクを開く。［コピー］→ クリップボードへ。どちらのあとも「送りましたか？」［送った］［送っていない］を出す。
  - ［送った］→ ContactLog（kind 'koekake'、via 'line_link' か 'copy'）を作り、候補から外れる（クールダウン、6.6）。
  - ［今回は見送る］→ Customer.snoozeUntil を設定する（2週間＝今日＋14日、次の周期まで＝今日＋目安の間隔の日数）。［連絡しないにする］は contact.permission を 'no' にする。LocalCounters.koekakeSkipped を1増やす。
  - **所属サロンの顧客**を顧客カードから開いた場合は、文面の前に注意を必須で出す:「この方のデータの管理者は所属サロンです。所属先の了解なく個人の連絡先から案内すると、契約や法令上の問題になることがあります。所属先のルールで認められている場合だけ続けてください。」［やめる］［認められているので続ける］。続けた場合は ContactLog.stewardWarningAcked を true にし、自分用の予約リンクは入れない。
- **空の状態**: 来店記録がない客は「最終来店が入っていないため、文面を作れません」＋［来店を追加］。
- **エラー時**: 4.3 のクリップボード・LINE のエラーと同じ。テンプレートの差し込みに失敗した語（不明な差し込み）は文面に残し、黄色で示す。

### 4.6 S5 顧客カード（前回の再現）

- **目的**: 施術前・声かけ前に、その人の前回と次回の目安を1画面で見る。
- **表示**:
  - 呼び名、かな、LINE表示名（任意）、一言メモ（上部に固定）。
  - バッジ: データの管理者（「所属サロン」のときだけ目立たせる）、獲得経路、連絡（OK／未確認／しない）、「はじめて」。
  - いつもの周期（例「約8週（直近3回）」。計算できないときは「まだ計算できません（来店2回から）」）。
  - 次回の目安日と根拠、今の区分（予約あり／今日／確認待ち／まだ／そろそろ／ご無沙汰／離れたかも／1年以上来ていない／リストから外した）。
  - 直近3回の来店: 日付、メニュー、次回の約束、レシピメモ、会話メモ、金額（入っていれば）。［すべての来店］で全件。
  - 連絡履歴（直近5件）: 日付、声かけ／またねカード、LINE／コピー。
  - 「お客様への伝え方の例」（折りたたみ）: 「次回の目安のころにお知らせするため、お名前（呼び名）とご来店の記録を、私のスマホの中だけに残しています。お知らせが不要なときは、いつでも言ってください。」。「法的な助言ではありません。必要な対応はご自身で確認してください」と添える。
- **操作**: ［来店を記録］［声をかける］［今回は見送る］［編集］［リストから外す（来なくなった・引っ越しなど）］［削除］。編集は1文字ごとに自動保存（0.3秒の間をおいて保存）。削除は来店・連絡履歴もまとめて消し、10秒間取り消せる。
- **空の状態**: 来店記録がない客は「最終来店を入れると、次回の目安が出ます」＋［来店を追加］。
- **エラー時**: 保存に失敗したら欄を赤くし「保存できませんでした」と出す。入力は画面に残す。

### 4.7 S6 お客様一覧とざっくり登録

- **目的**: 顧客を探す。初日から「声をかけてもよさそうな人」が出るよう、少ない項目で手早く登録する。
- **一覧の表示**: 検索（呼び名・かなの前方一致）。並べ替え（目安日が近い順／最終来店が古い順／名前順）。フィルタ（すべて／声かけ候補／確認待ち／1年以上来ていない／所属サロン／連絡しない／リストから外した）。各行に呼び名・区分・最終来店・目安日。
- **ざっくり登録の表示**:
  - 上部に「この登録の共通設定」: データの管理者（本人／所属サロン、**必須で選ぶ**）、獲得経路（本人SNS／本人minimo／本人LINE／本人のその他／紹介／サロン媒体／サロンからの引き継ぎ／不明）。獲得経路で「サロン媒体」か「サロンからの引き継ぎ」を選ぶと、データの管理者の初期値を「所属サロン」にする（変更できる）。
  - 行: ［呼び名］［最終来店（「8月」「2026-08」「8/22」など）］［主なメニュー（チップ）］。行ごとに管理者と経路を変えられる。
  - ［＋行を追加］。改行キーで次の欄へ進む。
- **操作**: 呼び名が入った行から順に自動保存する。最終来店は 6.12 の規則で解釈し、年月だけなら「おおよそ」の来店記録（source 'bulk'）を作る。保存すると、その場でホームの候補に反映される。
- **空の状態**: 一覧が0人のとき「まだお客様がいません」＋［ざっくり登録］［サンプルで試す］。
- **エラー時**: 最終来店が読めないとき「読み取れませんでした（例: 8月、2026-08、8/22）」と欄の下に出し、その行は来店なしで保存する。呼び名が21文字以上なら「20文字までにしてください」。同じ呼び名がすでにいるときは「同じ呼び名の方がいます」と出す（保存は止めない。呼び名に区別を足すよう促す）。

### 4.8 S7 わたしの再来ボード

- **目的**: 自分の行動と結果を、先月の自分とだけ比べる。効果を証明する画面ではない。
- **表示**（数字は3つだけ。計算は 6.9）:
  1. **稼働顧客数**: 「○人（最終来店が1年以内）」と「先月末 ○人」。
  2. **次回の約束あり**: 「今月 ○件中○件（予約○・目安○）」と「先月 ○件中○件」。率（%）は出さない（件数が少ないうちは率が大きく揺れるため）。
  3. **声かけと戻り（直近60日）**: 「声かけした人 ○人 → その後来店 ○人」と「声かけしなかったご無沙汰の人 ○人 → その後来店 ○人」。下に「比べるための事実です。声かけの効果を示すものではありません。人数が少ないうちは偶然の差が大きくなります」。
  - 下部に固定で「比べる相手は業界平均ではなく、先月のあなたです（個人美容師の信頼できる基準値はありません）」。
  - ［数字をコピー（名前は含まない）］: 上の3つ、直近28日の来店記録件数、声かけ件数、見送り件数、［実は来ていた］の回数、使い始めた日、最後のバックアップ日をテキストにしてコピーする。試用者が任意で作り手に送るためのもの。
- **操作**: 各数字をタップすると、その内訳の顧客一覧を出す（名前は端末内の表示だけ）。
- **空の状態**: 来店記録がないとき「来店を記録すると、ここに数字が出ます」。今月の記録が0件なら「今月の記録はまだありません」（0%とは出さない）。
- **エラー時**: 計算に失敗したら、その数字だけ「計算できませんでした」と出し、他の数字は表示する。
- **出さないもの**: 金額、売上、業界平均、月別のグラフ、獲得経路別の率、予測。

### 4.9 S8 設定とデータ

- **目的**: 初期値の調整、データの保護、バックアップ、データの持ち主の確認。
- **表示と操作**（セクションごと）:
  - **自分のこと**: 名前（文面の署名）、予約リンク（自分用・所属サロン用。https:// で始まるURLだけ受け付ける）。

### 4.10 文面のテンプレート（初期値）

差し込み（{ }）の中身は 6.10 で決める。中身が空になった差し込みを含む行は、行ごと消す。

**声かけ（初期値）**

```
{呼び名}さん、こんにちは。
美容師の{自分の名前}です。
前回の{前回のメニュー}から{経過}ほどたちましたが、髪の調子はいかがですか？
ご予約はこちらからどうぞ。 {予約リンク}
気になることがあれば、このままお返事ください。
```

**またねカード（初期値）**

```
{呼び名}さん、今日はありがとうございました。
今日のメニュー：{今日のメニュー}
次回の目安：{次回の目安}
ご予約はこちらからどうぞ。 {予約リンク}

```

- どちらにも割引・クーポン・期限つきの誘い文句を入れない（TDB が指摘する、割引で値上げが浸透しない問題を避ける）。
- 会話メモ・レシピメモは自動で差し込まない（個人的な話題や健康の話が意図せず送られるのを防ぐ）。

### 4.11 S9 ロック画面（PINを設定したときだけ）

- **目的**: 端末を置いたまま席を離れたときなどの覗き見を防ぐ。
- **表示**: PINの入力欄、［PINを忘れた］。「これは覗き見防止で、データの暗号化ではありません」。
- **操作**: 正しいPINで解除。［PINを忘れた］→「PINを解除するには、この端末のデータをすべて消す必要があります。バックアップがあれば、消したあとに戻せます」＋確認2回。
- **空の状態**: なし。
- **エラー時**: 間違えると「PINが違います」。5回続けて間違えると30秒入力できない（仮の値）。

### 5.2 保存先

- IndexedDB のデータベースを2つに分ける: 本番用 `matane`、サンプル用 `matane-sample`。どちらを開くかだけ localStorage（`matane.activeDb`）に置く。localStorage が使えないときは本番用を開く。
- ストア: `customers`、`visits`（索引: customerId、date）、`menus`、`contacts`（索引: customerId、date）、`templates`、`settings`、`drafts`、`counters`、`restorePoint`。
- 整合のルール:
  - 顧客を削除すると、その顧客の来店記録と連絡記録も消す。
  - 来店記録の日付は今日以前。`next.kind === 'booked'` の日付は来店日より後。
  - 顧客の stewardship と contact は必須（初期値は contact.permission = 'unknown'）。
  - schemaVersion は1。将来の版の読み込みでは移行処理を通す。

### 5.3 安全情報と同意にあたる型

- **ContactConsent**: お客様に連絡してよいかと、確かめた日・方法。
- **Stewardship**: データの管理者（本人／所属サロン）と獲得経路。持ち出しの防止に使う。
- **ContactLog.stewardWarningAcked**: 所属サロンの顧客に、注意を確認したうえで連絡した記録。
- **Settings.notice**: 利用者（美容師）が「データの持ち主・持ち出しの注意」を確認した日時と文面の版。
- **健康情報の型は作らない**（7.2）。アレルギー・既往歴・服薬・妊娠などを入れる欄がないことを、型の段階で保証する。メモに健康のことが書かれた場合は detectHealthWords（6.13）で注意を出すだけで、保存は止めない。

## 6. 計算ロジック

すべて純粋関数として作り、引数に「今日」と設定を渡す（テストで時計を 2026-11-07 に固定できるようにする）。削除印（deletedAt）のついたデータは計算から除く。

### 6.1 日付・保存の基本

- `daysBetween(a, b)` = (UTC日付としての b − a) ÷ 86,400,000。ローカル日付の文字列を `Date.UTC(y, m-1, d)` に直して計算し、夏時間やタイムゾーンの影響を受けない。
- `addWeeks(d, n)` = d + 7n 日。
- `addMonths(d, n)` = 同じ日付の n か月後。その月にその日がなければ月末にそろえる。
  - 例: 2026-08-31 + 1か月 = 2026-09-30、2026-12-31 + 2か月 = 2027-02-28、2026-11-07 + 2か月 = 2027-01-07。
- **下書き**: フォームの入力は、最後の入力から0.3秒後に Draft として保存する。pagehide と visibilitychange（hidden）のときはすぐ保存する。フォームを開くと下書きがあれば戻す。［保存］が成功したら下書きを消す。
- **削除と取り消し**: 削除はまず deletedAt を付けるだけにし、10秒間「元に戻す」を出す。10秒たつか画面を移ったら完全に消す。アプリが途中で閉じた場合に残った削除印つきのデータは、次の起動時に完全に消す。

### 6.2 来店記録の整え方

1. 削除印つきと、日付が今日より後のもの（あってはならないが念のため）を除く。
2. 日付の古い順に並べる。同じ日の記録が複数あれば、周期の計算では1回として数える。
3. 「最終来店」＝日付が最も新しい記録。同じ日なら createdAt が新しいほう。
4. 年月だけの記録（dateApprox = 'month'）は、最終来店の日付としては使うが、周期の計算には使わない。

### 6.3 いつもの周期（personalCycleDays）

```
入力: その客の来店記録（6.2 で整えたもの）、今日
1. dateApprox のない記録の日付を重複なしで並べる: d1 < d2 < … < dn
2. 間隔 g_i = daysBetween(d_i, d_{i+1})
3. 7 ≤ g_i ≤ 365 のものだけ残す（7日未満はお直し・重複、365日を超えるものは周期ではなく空白とみなす）
4. 残った間隔のうち新しいほうから最大5つを使う
5. 1つ以上あれば、その中央値を四捨五入した日数。偶数個なら中央2つの平均。0個なら null
```

| ケース（間隔の並び） | 結果 |
|---|---|
| 56, 56, 56 | 56 |
| 60, 60, 95 | 60 |
| 60, 70 | 65 |
| 42, 49 | 46（45.5 を四捨五入） |
| 5, 60 | 60（5 は除く） |
| 400, 60 | 60（400 は除く） |
| 6つ: 30, 40, 50, 60, 70, 80 | 60（新しい5つ 40〜80 の中央値） |
| 来店1回だけ | null |
| 年月だけの記録＋正確な記録1回 | null |

### 6.4 次回の目安日（computeDue）

最終来店を L とし、その記録の next を見る。上から順に、最初に当てはまったものを使う。

| 優先 | 条件 | 目安日 D | basis |
|---|---|---|---|
| 1 | next.kind = 'booked' で、bookingResolution がない | next.date | booked |
| 2 | next.kind = 'agreed' | 週なら addWeeks(L, n)、月なら addMonths(L, n) | agreed |
| 3 | いつもの周期が null でない | L + 周期 | personal |
| 4 | L のメニューに目安の日数を持つものがある | L + その中の最小値（いちばん早く戻ってくるメニューに合わせる） | menu |
| 5 | 上のどれでもない | L + globalDefaultIntervalDays（初期87） | global |

- `'omakase'`、`'none'`、予約を「来なかった」と確認したものは、3以降へ進む。
- I = daysBetween(L, D)、E = daysBetween(L, 今日)。

| ケース | 結果 |
|---|---|
| L=2026-11-07、next = 予約 2026-12-19 | D=2026-12-19、booked |
| L=2026-11-07、next = 目安6週 | D=2026-12-19、agreed |
| L=2026-08-31、next = 目安2か月 | D=2026-10-31、agreed |
| L=2026-12-31、next = 目安2か月 | D=2027-02-28、agreed |
| おまかせ、周期56 | D=L+56、personal |

| おまかせ、周期なし、メニュー［カット（なし）］ | D=L+87、global |

### 6.5 区分の判定（status）

浮動小数の誤差を避けるため、割合は整数で比べる。

```
1. 顧客が archived                         → 'archived'
2. 来店記録がない                           → 'no_data'
3. 最終来店の next が 'booked'（未解決）:
     予約日 > 今日 → 'booked'
     予約日 = 今日 → 'today'
     予約日 < 今日 → 'confirm'
4. E > dormantDays（365）                   → 'dormant'
5. 100×E < soonPct×I（85）                  → 'not_yet'
6. 100×E ≤ 100×I                            → 'soon'     （85% 以上 100% 以下）
7. 100×E ≤ lapsedPct×I（150）               → 'overdue'  （100% を超え 150% 以下）
8. それ以外                                  → 'lapsed'   （150% を超える）
```

境界のテスト（I = 60 の例）:

| E | 判定 | 理由 |
|---|---|---|
| 50 | not_yet | 5000 < 5100 |
| 51 | soon | 5100 ≥ 5100 |
| 60 | soon | ちょうど目安日 |
| 61 | overdue | 目安日の翌日 |
| 90 | overdue | 9000 ≤ 9000（ちょうど150%） |
| 91 | lapsed | 150% を超える |
| 365 | lapsed | dormantDays ちょうどは含まない |
| 366 | dormant | 365 を超える |

I = 42 の例: E=35 は not_yet（3500 < 3570）、E=36 は soon、E=42 は soon、E=43 は overdue、E=63 は overdue、E=64 は lapsed。

### 6.6 声かけ候補（eligibility）

```
候補にする条件（すべて満たす）:
  a. status が 'soon' / 'overdue' / 'lapsed' のどれか
  b. 除外理由に当てはまらない（下の順に調べ、最初に当てはまった理由を記録する）
     1. stewardship.steward = 'salon'                         → 'salon'
     2. contact.permission = 'no'                             → 'no_contact'
     3. onlyContactOkInList が true で permission ≠ 'ok'       → 'not_confirmed_ok'
     4. snoozeUntil があり、今日 ≤ snoozeUntil                  → 'snoozed'
     5. 最終来店日より後の koekake の数 ≥ maxContactsPerGap（2） → 'max_contacts'
     6. 最後の koekake の日を C として daysBetween(C, 今日) < cooldownDays（30） → 'cooldown'

並べ方: 遅れの割合 E/I の大きい順（E1×I2 と E2×I1 を比べる）。同じなら E の大きい順、さらに同じなら呼び名の五十音順
表示: 先頭から listLimit（5）人。残りは［ほかに○人］
ラベル:
  permission = 'unknown'                         → 'contact_unconfirmed'（連絡OKは未確認）
  最終来店が dateApprox                           → 'approx_last_visit'（最終来店はおおよそ）
  dateApprox のない来店が1回だけ、かつ source ≠ 'bulk' → 'first_visit'（はじめて）
要約: status が a に当てはまるのに除外された人を、理由ごとに数える
```

| ケース | 結果 |
|---|---|
| 最後の声かけが29日前 | 除外（cooldown） |
| 最後の声かけがちょうど30日前 | 候補 |
| 最後の来店のあとに声かけ2回 | 除外（max_contacts） |
| snoozeUntil = 今日 | 除外（snoozed） |
| snoozeUntil = 昨日 | 候補 |
| 所属サロンの顧客で overdue | 除外（salon） |
| permission = 'unknown' | 候補（ラベルつき）。onlyContactOkInList が true なら除外 |

### 6.7 今日のお客様・来た？の確認

```
今日のお客様（今日 = T）:
  (a) 日付が T より前の記録のうち最新のものが next = 予約(T) で未解決、または
  (b) 日付が T の来店記録がある
  の顧客。(b) なら「記録済み」。並びは「まだ」→「記録済み」、それぞれ呼び名順

  status = 'confirm' の顧客（最終来店の予約日が T より前で、それ以降の記録がない）

  確認待ちの顧客は声かけ候補に入れない（6.6 の a に当てはまらない）
```

- ［来なかった］は最終来店の記録に bookingResolution = 'not_visited' を付ける。以後は 6.4 の3以降で目安を出す。

### 6.8 記録の鮮度とバックアップの催促

```

記録停止の表示: 顧客が1人以上いて、daysBetween(R, T) > staleRecordDays（7）、

  ［休みでした］→ staleDismissedUntil = T + 7

催促の表示: daysBetween(B, T) > backupReminderDays（14）
サンプル用データベースを開いているときは、どちらも出さない
```

### 6.9 わたしの再来ボード

```
lastVisitOn(c, X) = 日付が X 以前の来店記録のうち最新の日付

1) 稼働顧客数(X) = 削除・archived でない顧客のうち、
     lastVisitOn(c, X) があり、daysBetween(lastVisitOn(c, X), X) ≤ dormantDays の人数
   表示: 稼働顧客数(T) と 稼働顧客数(先月の末日)

2) 次回の約束あり(月 M):
     V_M = 日付が月 M にあり、source ≠ 'bulk' の来店記録
     n = |V_M|、k = next.kind が 'booked' か 'agreed' の件数（内訳 b = booked、a = agreed）
   表示: 「n件中k件（予約b・目安a）」。今月と先月。n = 0 なら「記録なし」

3) 声かけと戻り（W = compareWindowDays = 60、S = T − W）:
     A = (S, T] に koekake がある顧客
         c1 = その期間の最初の koekake の日
         戻った = c1 < 日付 ≤ T の来店記録がある
     B = A に入らず、削除・archived でなく、steward = 'self'、permission ≠ 'no' で、
         statusAt(S) が 'overdue' か 'lapsed' の顧客
         （statusAt(S) は、日付が S 以前の来店記録だけを使い、今日 = S として 6.5 を当てたもの）
         戻った = S < 日付 ≤ T の来店記録がある
   表示: 「声かけした人 |A|人 → その後来店 (Aのうち戻った)人」
         「声かけしなかったご無沙汰の人 |B|人 → その後来店 (Bのうち戻った)人」
```

- 管理者・連絡可否は計算時点の値を使う（過去の値は保存しない）。
- 金額への換算、率の表示、業界との比較はしない。

### 6.11 1行入力の解析（parseOneLine）

```
入力: 文字列、来店日 V、顧客一覧、メニュー一覧、（選択済みの客）
1. 正規化: NFKC、前後の空白を除く。照合用にはカタカナをひらがなにそろえる
2. 区切り: 空白、「、」「，」「,」「・」「+」「＋」で分ける
3. 語ごとに上から判定:
   a. /^(\d{1,2})[\/月](\d{1,2})日?$/ → 予約日。年は V の年。
      その日付が V より前なら翌年。V と同じ日なら「予約日は来店日より後に」として読み取れなかった語へ
      存在しない日付（2/30 など）は読み取れなかった語へ
   b. /^(\d{1,2})(週|週間|w)後?$/i で 1〜26 → 目安（週）
   c. /^(\d{1,2})(か月|ヶ月|カ月|ケ月|ヵ月)後?$/ で 1〜12 → 目安（月）
   d. 「おまかせ」 → おまかせ
   e. /^(\d+)円$/ または /^\d{4,6}$/ → 金額
   f. メニュー名・別名を先頭から最長一致で切り分け、間の「と」は読み飛ばす。
      語全体を切り分けられたら、そのメニューを足す（重複は1つに）
   g. それ以外で、まだ名前が決まっていなければ名前とする。
      末尾の「さん」「さま」「様」「ちゃん」「くん」「君」を除き、呼び名・かなの前方一致で候補を探す
   h. どれにも当たらない語 → 読み取れなかった語
4. 次回の指定が複数あれば最後のものを使い、「次回の指定が2つありました」と出す
出力: { customerMatches: Customer[]; menuIds: ID[]; next?: NextPlan; price?: number; unparsed: string[] }
```

|---|---|
| ゆず カットカラー 6週 8800 | 客＝ゆず、メニュー＝カット・カラー、次回＝6週、金額＝8,800円 |
| ゆずさん カットとカラー 2ヶ月 | 客＝ゆず、メニュー＝カット・カラー、次回＝2か月 |
| もみじ 白髪染め 12/19 | 次回＝予約 2026-12-19 |
| もみじ 白髪染め 1/9 | 次回＝予約 2027-01-09 |
| もみじ 白髪染め 11/7 | 読み取れなかった語［11/7］（来店日と同じ） |
| ゆず かっと からー | メニュー＝カット・カラー（ひらがなでも照合） |
| ゆ カット | 客の候補＝［ゆず］（前方一致） |
| さくら カット | 客の候補なし →「新しいお客様として登録」を出す |
| ゆず カット 7 | 読み取れなかった語［7］ |

## 7. 安全と個人情報の設計

### 7.1 データの持ち主

- 記録の持ち主は、使っている美容師本人。ただし「所属サロン」を管理者にした顧客のデータは、所属サロンのものとして扱う。
- 作り手（omicreate）は記録を受け取らない。このアプリにはサーバーも解析ツールも Cookie もない。omicreate の既存アプリは匿名の利用データを送っているが、またね帳のプロトタイプは**何も送らない**（Content-Security-Policy で `connect-src 'self'` にし、外部への通信を作らない）。
- この説明を、初回の S0、設定の「このアプリについて」、バックアップの画面に出す。
- 個人情報保護法は規模を問わず適用される（rules）。お客様の個人情報を扱う事業者は美容師本人（または所属サロン）であり、アプリはその道具であることを明示する。

### 7.2 健康情報と、集めないもの

- 健康情報（アレルギー・皮膚疾患・既往歴・服薬・妊娠など）の欄は作らない。型にも入れない（5.1）。
- メモ欄には常に注意を出し、健康に関する語を入れると注意する（6.13）。
- 電話番号・メールアドレス・住所・生年月日・性別・写真は集めない。呼び名だけで使える。
- 会話メモ・レシピメモは文面に自動で入れない。
- 「またね帳はカルテの代わりではない。安全に関わる記録は今のカルテで」と初回に明示する。
- 16歳未満の顧客は年齢の欄がないため判定しない。改正個人情報保護法（2026年7月公布）で法定代理人の同意が入ることを踏まえ、連絡は保護者を通すよう「お客様への伝え方の例」に添える（施行日は未検証）。

### 7.3 連絡の同意と、持ち出しの防止

- **連絡の同意**: 顧客ごとに「連絡OK／しない／未確認」と、確かめた日・方法を残す。会計時の来店記録で1タップで更新できる。「しない」の人は候補に出さない。「未確認」の人は候補に出すがラベルを付ける。設定で「連絡OKの人だけを候補にする」に切り替えられる。
- **送るのは常に利用者**: 自動送信・一斉送信はしない。送る前に文面の全文と宛先の目印（LINE表示名）を見せ、送ったかどうかは本人が［送った］で記録する（誤送信の防止。competitors_global の誤送信レビューへの対応）。
- **データの管理者と獲得経路**（gap_2）:
  - 登録時に必須。サロン媒体・サロンからの引き継ぎを選ぶと、管理者の初期値を「所属サロン」にする。
  - 所属サロンの顧客は、声かけ候補に出さない。顧客カードから声をかけるときは注意の確認を必須にし、自分用の予約リンクを入れない。
  - 平文の書き出しには含めない（含める設定も作らない）。
  - ［所属サロンの顧客をまとめて削除］で、退店時に該当する顧客と来店・連絡の記録を消せる（確認2回）。
  - 初回と設定に「このアプリを違法な持ち出しや勧誘に使わないでください。所属先との契約（持ち出し禁止・非勧誘など）を確認してください」と出す。
  - CSV の取り込みは作らない（サロン名義の台帳を取り込む入口にしない）。
- **法令で未検証の点**: 個人LINEでの営業連絡が LINE の規約上どう扱われるか、特定電子メール法がどこまで当てはまるか（またね帳はメールを送らないが、利用者がコピーした文面をメールに貼る可能性はある）。公開前に確認する（11章）。

### 7.4 端末内保存のリスクと対策

| リスク | 対策 |
|---|---|
| 端末の紛失・盗難で、顧客の呼び名やメモが見られる | OSの画面ロック（パスコード・生体認証）を必ず使うよう、初回とPIN設定画面で案内する。アプリ内PIN（任意）と自動ロック。集める項目を最小にする |
| 席を離れたときの覗き見 | アプリ内PIN。アプリを離れて1分以上たって戻ったとき、または5分操作がないとき（仮の値）にロックする |
| バックアップファイルが LINE やメールで流れて漏えいする | バックアップは**暗号化が既定**。平文の書き出しは警告の確認を通した別操作にし、所属サロンの顧客を含めない |
| 機種変更・ブラウザのデータ削除・iOS で一定期間使わないとサイトデータが消える場合（案1・案4の記載。実機で未検証） | ホーム画面への追加の案内、永続保存（navigator.storage.persist）の要求と状態表示、14日（仮の値）ごとのバックアップの催促 |
| バックアップから戻すときに、今のデータを誤って上書きする | 戻す前の状態を RestorePoint に1回分保存し、［戻す前の状態に戻す］ができる |
| 入力途中で消える | 下書きの自動保存、削除の取り消し（6.1） |

**PIN の作り**:
- 4〜8桁の数字。端末に保存するのは PBKDF2-SHA256 で作ったハッシュと塩（16バイト）、反復回数だけ。
- PIN は画面を隠すだけで、端末内のデータは暗号化しない。画面にも「覗き見防止で、暗号化ではありません」と書く。
- PIN を忘れたら、データをすべて消して初期化するしかない（消さずに解除できると、PIN の意味がなくなるため）。設定時にこのことと、バックアップを取っておくことを伝える。
- 5回続けて間違えると30秒待つ（仮の値）。

**暗号化バックアップの作り**:
- Web Crypto API を使う。パスフレーズ（8文字以上）から PBKDF2-SHA256 で鍵を作り、AES-GCM（256ビット、IV 12バイト、塩16バイトは毎回ランダム）で BackupPayload を暗号化する（形式は 5.1 の EncryptedBackupFile）。
- 反復回数は実装時に OWASP の Password Storage Cheat Sheet の現行推奨値を確認して決め、ファイルに記録する（ファイル側に値を持つので、後から上げても古いファイルを読める）。
- パスフレーズは保存しない。忘れると戻せないことを、書き出しの前に確認してもらう（チェックを入れないと書き出せない）。
- 読み込み時にパスフレーズが違うか、ファイルが壊れていれば「パスフレーズが違うか、ファイルが壊れています」と出し、今のデータは変えない。
- 新しい版のファイル（version が大きい）は「新しい版のファイルです。アプリを更新してください」と出して読み込まない。
- 「高度な暗号化」にあたるか、漏えい時の報告が不要になるかは確認できていない（rules：個人情報保護委員会の資料は未確認）。そのため、アプリ内で「報告が不要」などとは書かない。
- Web Crypto は安全な接続（https か、開発用に自分の端末で開いたページ）でしか動かない。プロトタイプもその条件で動かす。

**平文の書き出し**:
- JSON（BackupPayload から所属サロンの顧客とその記録を除いたもの）と CSV（1行＝1来店。呼び名、来店日、おおよそか、メニュー、次回、金額、レシピメモ、会話メモ、管理者、獲得経路。UTF-8・BOMつき）。
- 書き出しの前に「暗号化されていないファイルです。LINEやメールで送らず、自分だけが見られる場所に保存してください」を確認してもらう。

### 7.5 その他の注意

- 1台を複数人で使うことは想定しない。
- アプリの切り替え画面やスクリーンショットに内容が写ることは、Webアプリからは防げない。設定の説明に書く。
- 端末をなくしたときにアプリ側から遠隔で消す手段はない。OS の端末を探す機能・遠隔消去を使うよう案内する。

## 10. やらないこと・考えないこと

| やらないこと | 理由 |
|---|---|
| 予約の受付・空き枠の管理・カレンダー同期 | 既存の予約サイトや LINE に任せ、予約リンクでつなぐだけにする。競合せず併用する |
| 予約通知の貼り付け取り込み（案4） | HPB・minimo の通知文の実物を確認できておらず、このセッションでは精度を確かめられない。次の候補（11章） |
| 自動送信・一斉配信・LINE公式アカウントの API・Instagram DM 連携・Web Push | サーバーと API キーが要る。LINE の無料枠200通の問題がある。自動配信は「営業っぽさ」を強める |
| SMS・メールの起動、電話番号・メールアドレスの保存 | 特定電子メール法の当てはまり方を確認していない。データを最小にする |
| 割引クーポンの文面・自動発行 | 割引で値上げが浸透しないという TDB の指摘。初期の文面に割引を入れない |
| 決済・キャンセル料・キャンセル対策 | キャンセル率の重さが過大に見積もられている（点検役）。決済は持たない |
| DM 返信の半自動化・予約窓口の一本化 | 「最優先」の根拠がない（同期の不満1件、DM返信0件） |
| 健康情報（アレルギー・既往歴など）の記録、施術上の注意フラグ、カラー前チェック、パッチテスト案内 | 要配慮個人情報で、同意と暗号化の設計が固まっていない。またね帳はカルテの代わりではない。安全の価値は認めるが、扱うなら同意・暗号化・責任範囲を別に設計してから（案2の領域） |
| 構造化カラーレシピ・放置タイマー | 自由メモと「前回を複製」で足りる。タイマーは iOS の制約があり作りが重い |
| 写真 | 容量、iOS のデータ削除、バックアップの肥大、写真の同意、漏えいしたときの影響 |
| 再来ボードの月別推移グラフ、目安共有率の別指標 | 初月は空になる。数字3つと先月比で足りる |
| 獲得経路別の2回目来店率、経路別の費用・獲得単価、新規の2回目来店率 | 1人の美容師の新規客数では率が大きく揺れる。経路の欄だけ残す |
| 値上げ前後の再来チェック、値上げシミュレーター | 主軸から外れる。データが数か月たまるまで意味がない |
| 再来の金額換算、業界平均との比較、失客率の予測 | 因果のない数字を成果に見せてしまう。信頼できる基準値がない |
| 手取り・売上・経費・インボイス・確定申告 | 案3の領域。二重入力が増え、税制や手数料の改定に追い続ける負担が大きい |
| CSV の取り込み | サロン名義の台帳を取り込む入口になる。正当な権限を確かめる設計ができていない |
| 口調の切り替え・季節の一言・テンプレートの複数化 | テンプレート1本を手直しして送れば足りる |
| 退店モードの本格版（契約条件の入力、顧客への同意の取り直し） | MVP では既定の除外と一括削除だけにする。本格版は利用者の声を聞いてから |
| クラウド同期・複数端末・スタッフ間の共有・ログイン | サーバーが要る。omicreate の方針に合わない |
| 外部 API を使った AI の文面生成 | API キーとサーバーが要る。文面はテンプレートと本人の手直しで作る |
| 課金・広告・解析ツール・Cookie | omicreate の方針。課金余地は未検証 |
| 高齢オーナー向けの大きな文字の専用モード | プロトタイプの主対象ではない（OS の文字サイズ設定には追従する） |
| 出張美容の予約 | 美容師法で例外に限られる |
